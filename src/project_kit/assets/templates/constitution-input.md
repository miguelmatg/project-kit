## Core principles

### I. Spec-driven development (NON-NEGOTIABLE)
Every feature follows specify, clarify, plan, tasks, implement. There is no product code
without an approved spec. Each spec lives in its own branch `NNN-name`, created from
`{{branches.develop}}`, and in `specs/NNN-name/`. Trivial changes (typos, dependency bumps,
configuration) may go as `chore/*` without a spec.

### II. Test-first and verifiable quality
Domain logic is written test-first (red, green, refactor). Integration tests cover the
boundaries between components, and contract tests cover every API or schema change. Nothing
is merged without a green CI. A fixed bug includes the test that reproduces it.

### III. Security and secrets
Authorisation is enforced on the server side. Secrets live only in a secrets manager or in
the hosting platform's secrets, never in the repository (a `.env.example` without values is
versioned instead). Personal data is handled according to the applicable regulation and that
handling is documented in the spec that touches it.

### IV. Automation and reproducibility
Infrastructure and processes are versioned configuration. There are no manual changes that
are not reflected in the repository, and critical tasks are idempotent and retryable.

### V. Simplicity
Choose the simplest solution that validates the product. Any extra complexity is justified in
writing, in the plan's complexity tracking or in an ADR.

### VI. Decisions in writing
Every cross-cutting decision (stack, authentication, data, deployment) is recorded as an ADR
in `docs/adr/`.

## Development workflow and quality gates

- Permanent branches: `{{branches.main}}` (released product), `{{branches.release}}`
  (testing and acceptance) and `{{branches.develop}}` (development).
- Working branches start from `{{branches.develop}}`: `NNN-name` (one per spec), `chore/*`,
  `docs/*` and `fix/*`. `hotfix/*` starts from `{{branches.main}}`.
- Promotion flows `{{branches.develop}}` to `{{branches.release}}` to `{{branches.main}}`. A
  hotfix goes to `{{branches.main}}` and `{{branches.release}}` and is then propagated back
  to `{{branches.develop}}`.
- Squash merge into `{{branches.develop}}`; merge commit into `{{branches.release}}` and
  `{{branches.main}}`. Releases are tagged `vX.Y.Z` (SemVer) on `{{branches.main}}`.
- Commits follow Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `test:`,
  `refactor:`, `ci:`).
- Everything goes through a pull request. There is no direct push to a permanent branch.
- Branch protection is not configured by project-kit. Where the hosting plan does not offer
  it (for example a private repository on a free GitHub plan) these rules are followed by
  discipline; where it is available it should be enabled.
- The project board is the source of truth for planning. A card becomes Ready only when it
  has acceptance criteria. Work in progress is limited to one spec In progress and one In
  review.
- Definition of Done: acceptance criteria met, tests green in CI, documentation and ADRs
  updated, the pull request references its issue (`Closes #N`) and the working branch is
  deleted.
